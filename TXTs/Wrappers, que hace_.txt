El archivo Wrappers.c actúa como la interfaz o puente (trampolín) físico y lógico entre el núcleo del emulador (escrito en C) y el código de máquina PowerPC (PPC) que el recompilador dinámico acaba de generar en tiempo real.


La forma en que logra esto se divide en cuatro mecanismos principales:


* El salto de ejecución físico (dyna_run): Es la función que literalmente transfiere el control de la CPU de la Wii hacia el bloque de código recién traducido. Lo hace inyectando ensamblador puro (__asm__ volatile) dentro del código C. Primero, ancla variables críticas a registros físicos fijos (ej. el registro r29 siempre apuntará a la memoria RDRAM del N64, y r30 a la estructura de la función actual). Luego, guarda el estado de la CPU (como el Link Register) en la pila para saber cómo regresar, carga la dirección de memoria del código traducido en el registro contador (mtctr), y ejecuta un salto incondicional (bctr) para que el procesador comience a correr el código PPC nativo.
* * El bucle orquestador (dynarec): Es el corazón del emulador, un bucle infinito (while(!stop)) que decide qué hacer paso a paso. Su flujo lógico consulta el mapa de memoria (blocks_get) para ver si la dirección actual ya tiene un bloque recompilado. Si no existe o fue invalidado, invoca al traductor (recompile_block) para fabricarlo en el momento. Justo antes de ejecutarlo con dyna_run, la función intenta encadenarlo con el bloque que se ejecutó previamente (RecompCache_Link); de esta forma, la próxima vez que el código pase por ahí, la CPU saltará de un bloque PPC a otro directamente sin perder tiempo regresando a este bucle en C.
* * El manejo de excepciones de memoria (dyna_mem): Cuando el código ensamblador requiere realizar una operación de memoria que es muy compleja para el "fast-path" (como accesos de memoria desalineados mediante MEM_LWL o MEM_SWR, accesos al caché, o interacciones con hardware externo), abandona la ejecución en ensamblador y hace un callback a esta función en C. Aquí, un bloque masivo switch decodifica la petición, alinea los bits y opera sobre los arreglos de memoria en C. Crucialmente, cada vez que se realiza una escritura en memoria (MEM_SW, MEM_SB, etc.), esta función llama a invalidate_func(addr). Esto purga la caché del recompilador si el juego intentó reescribir su propio código ejecutable (código automodificable), evitando que el emulador corra instrucciones fantasma.
* * El salvavidas del intérprete (decodeNInterpret): Si el traductor encuentra una instrucción sumamente extraña, o si detecta un branch delay slot virtual que no puede empaquetar de forma segura en código nativo, inyectará una llamada a esta función. Ésta toma la instrucción MIPS cruda, averigua qué "opcode" es, y delega su ejecución paso a paso al arreglo original de funciones en C del intérprete clásico (interp_ops[MIPS_GET_OPCODE(mips)]()). Una vez procesada de forma lenta pero segura, devuelve el control al motor dinámico.
